# Arquitectura de WHArmy

Este documento resume las decisiones técnicas tomadas y el motivo de cada una, tal como pide la especificación del proyecto ("ante cualquier decisión de diseño importante, documentar brevemente el motivo"). Es un documento vivo: se actualiza según evoluciona el proyecto.

## 1. Por qué una app 100% estática (sin servidor propio)

El plan inicial preveía tres capas físicamente separadas: BBDD (Cloudflare D1), lógica de negocio (Cloudflare Workers) y frontend (React). Pero la aplicación se aloja en GitHub Pages, que **solo sirve archivos estáticos**: no puede ejecutar Workers ni ninguna otra pieza de servidor.

Decisión: mantener las **tres capas como separación arquitectónica** (datos / dominio / presentación), pero ejecutando las tres **dentro del navegador**, en el mismo bundle estático:

- **Datos**: SQLite real (vía [sql.js](https://sql.js.org), SQLite compilado a WebAssembly), no una simulación con JSON sueltos.
- **Dominio**: módulos TypeScript puros (`src/domain/`), sin dependencias de React ni de sql.js directamente — solo de los repositorios.
- **Presentación**: React, que nunca consulta la base de datos directamente, solo a través de los repositorios (`src/data/repositories/`).

El acoplamiento entre capas es el mismo que si estuvieran en procesos separados (cada una solo conoce la interfaz de la de abajo), simplemente no hay una red física de por medio. Esto **no compromete la posibilidad de añadir un backend real más adelante**: el día que haga falta (multi-usuario con datos privados, por ejemplo), solo se reescribe la implementación de los repositorios para llamar a una API en vez de a sql.js — el dominio y la UI no cambian.

> **Actualización (ver 8terdecies):** ese día llegó — el usuario pidió que los cambios de un usuario se vieran reflejados para los demás, así que `data/sqlite/client.ts` pasó de sql.js/IndexedDB local a llamar por HTTP a un Cloudflare Worker + D1 real (justo la arquitectura que este punto describía como "el plan inicial", ahora sí posible porque GitHub Pages solo aloja el frontend estático; el Worker se despliega y aloja aparte, en Cloudflare). Los repositorios (`src/data/repositories/`) no cambiaron su interfaz pública ni una línea de UI — exactamente como se predijo aquí.

## 2. Por qué SQLite en vez de "un JSON grande"

Los datos maestros (facciones, unidades, equipo, reglas...) son intrínsecamente relacionales: una unidad tiene reglas, equipo, mejoras, montura, opciones de mando... todo con relaciones N:M. Modelarlo en SQLite en vez de un JSON gigante da:

- Integridad referencial real (`FOREIGN KEY`), que un JSON no puede garantizar.
- Consultas declarativas (`JOIN`, `WHERE`) en vez de recorrer arrays a mano en cada componente — mucho menos código repetido.
- Una única fuente de la verdad literal: el mismo fichero `.db` es el que se consulta en cada pantalla; no hay riesgo de que dos partes de la app tengan "su propia copia" de los mismos datos con pequeñas diferencias.

## 3. Modelo de persistencia en el navegador (sin backend)

No hay servidor donde guardar los cambios que se hagan desde Administración. La solución:

1. `public/data/warhammer.db` es la **semilla**: se genera con `scripts/etl_datos_json.py` a partir de los datos de origen y se versiona en el repositorio Git. Es de solo lectura desde el punto de vista de la app en ejecución.
2. La primera vez que se abre la app, esa semilla se clona en **IndexedDB** del navegador. A partir de ahí, todas las lecturas y escrituras van contra esa copia.
3. Cada escritura (crear/editar/borrar desde Administración) exporta la base de datos completa (`db.export()`, unos cientos de KB) y la vuelve a guardar en IndexedDB. Como el conjunto de datos es pequeño, este export-en-cada-escritura es barato y evita construir un sistema de sincronización incremental que no hace falta con este volumen de datos.
4. Existe una función `resetToSeed()` para volver a los datos de fábrica, expuesta en la UI como "Restaurar datos de fábrica" en la barra superior.

Esto es deliberadamente una solución "por usuario y por navegador": cada persona que abra la app tiene su propia copia editable en su propio dispositivo. Es coherente con "sin autenticación, todos ven lo mismo" de la especificación actual, y dejará de ser necesario en cuanto se incorpore un backend (ver punto 5).

**Invalidación cuando cambia el esquema.** Un usuario que ya tenga una copia en IndexedDB de *antes* de un cambio en `db/schema.sql` (por ejemplo, la migración de perfiles del punto 4bis) se quedaría con tablas o columnas que el código nuevo ya no espera, y las consultas fallarían. Para que eso nunca se traduzca en una pantalla en blanco o cargando indefinidamente, `getDb()` comprueba `import_meta.schema_version` de la copia guardada contra `EXPECTED_SCHEMA_VERSION` (una constante en `src/data/sqlite/client.ts` que debe coincidir con `SCHEMA_VERSION` en `scripts/etl_datos_json.py`); si no coincide (o la tabla ni siquiera existe, señal de una copia muy antigua), se descarta sin más y se vuelve a clonar la semilla actual. **Al subir la versión del esquema hay que subir el número en los dos sitios.**

## 4. Atomización de las opciones de equipo y exclusividad automática

Los datos de origen (`HojaEjercito/datos.json`, herramienta "Manuscritos de Nuth") modelan el equipo como **paquetes ya combinados** (p. ej. `"2AM / A.Pesada / Escudo"` como una sola opción con un coste único), no como piezas atómicas (arma + armadura + escudo por separado). La primera versión de la importación preservaba esa granularidad tal cual; se ha sustituido por una descomposición automática en `scripts/etl_datos_json.py`, unidad por unidad:

- Los paquetes combinados (cualquier nombre con `/`) **no se insertan en `equipment_options`**: solo se registran sus piezas sueltas. Cada unidad recibe directamente el conjunto de piezas sueltas que aparecían en cualquiera de sus paquetes de origen, así que puede seguir comprando cualquier combinación real que ofrecía el origen (p. ej. Guerreros nómadas ofrecía "A2M / A.Pesada"+3 como paquete; ahora la unidad tiene "A2M"+2 y "A.Pesada"+1 como piezas sueltas independientes, combinables libremente). Esto eliminó del catálogo cualquier opción con "/", que había quedado redundante en cuanto existe la exclusividad automática (ver abajo) para impedir combinaciones ilegales.
- Cada pieza suelta se clasifica en una `category` (`armadura` / `escudo` / `arma_cac` / `arma_dist`) mediante un diccionario de nombres conocidos (`EQUIPMENT_CATEGORY` en el ETL). Los nombres no reconocidos quedan sin categoría (`NULL`), que es el valor por defecto más seguro: siempre combinable, sin restricción.
- **Exclusividad automática**: dos piezas de la misma unidad con la misma `category` se consideran alternativas excluyentes (no puedes llevar dos armaduras, o un arco Y una ballesta a la vez) y se registran en `equipment_incompatibilities` — SALVO que el origen las haya ofrecido combinadas alguna vez en cualquier paquete de cualquier unidad (`compute_compatible_pairs`, que sigue operando sobre los paquetes crudos del origen aunque ya no se inserten como filas propias), lo que se toma como evidencia real de que sí se pueden llevar juntas (p. ej. Montañeses ofrecía "Ballesta ligera / Hachas arrojadizas" como combo válido, así que esas dos NO se marcan excluyentes aunque ambas sean `arma_dist`). Se verificó este comportamiento explícitamente contra Montañeses (Enanos) antes de aplicarlo al resto del dataset: los tres huecos de esa unidad (Ballesta ligera, A2M, Hachas arrojadizas) resultan totalmente combinables entre sí, tal y como sugerían sus paquetes de origen.
- `equipment_incompatibilities` es la misma tabla que ya prevía el esquema para "equipo ilegal" — no ha hecho falta ningún concepto nuevo, solo poblarla automáticamente en vez de dejarla vacía. Nada la consume todavía (el constructor de listas "Ejércitos" es el que la usará para impedir combinaciones ilegales al montar una lista); de momento es solo dato de referencia, visible como subtítulo de categoría en el editor de equipo de una unidad.

Se han detectado ~40 nombres de equipo duplicados con costes distintos entre sí (probablemente variantes de precio por facción, o inconsistencias del origen): quedan como filas independientes, igual que antes. Desde la ficha de una unidad también se puede dar de alta una pieza de equipo nueva que no exista todavía en el catálogo (nombre + coste + categoría opcional), sin salir de la pantalla.

## 4bis. Una unidad puede tener varios perfiles de atributos

La primera versión modelaba el perfil de una unidad como una relación 1:1 (`units.base_profile_id`) y trataba monturas y carros como dos entidades aparte (`mounts`, `chariots`) con sus propias tablas de unión. Era un calco directo de cómo estaban repartidos los datos en el origen, pero no reflejaba la realidad del juego: **una unidad puede tener varios perfiles de atributos asociados a la vez**. Por ejemplo, un carro de guerra tiene simultáneamente su perfil base (la tripulación), el de su montura y el del propio carro — se comprobó contra los datos y hay 35 unidades así.

Se corrigió a una única tabla `attribute_profiles` (con `name` opcional: `NULL` cuando el perfil es el de la propia unidad, con valor cuando es un perfil reutilizable como una montura o un carro) más una relación N:M `unit_profiles(unit_id, profile_id, role)`, con `role` en `'base' | 'montura' | 'carro'`. Esto:

- Elimina la duplicación de las tres tablas casi idénticas (`attribute_profiles`, `mounts`, `chariots` tenían las mismas 9 columnas).
- Permite que una unidad tenga 1 perfil base + 0..N perfiles de montura + 0..N perfiles de carro, sin forzar cardinalidades falsas.
- Deja sitio para roles nuevos en el futuro (p. ej. si algún día hiciera falta un perfil distinto para un campeón) sin volver a tocar el esquema, solo añadiendo un valor al `CHECK` de `role`.

Los perfiles "base" se deduplican solo entre sí (dos unidades con las mismas 9 estadísticas comparten fila), y los de montura/carro entre sí — pero nunca se fusionan valores entre bolsas distintas, porque aunque coincidan numéricamente son conceptos distintos.

## 5. Preparado para autenticación futura (Firebase o equivalente)

La capa de dominio y la UI dependen solo de las **interfaces** de los repositorios (`FactionRepository`, `UnitRepository`, etc.), nunca de sql.js directamente. Cuando se añada un sistema de usuarios:

- Si cada usuario necesita sus propios datos privados (p. ej. sus listas de ejército guardadas), basta con implementar esos repositorios de "datos de usuario" contra Firestore (o equivalente) sin tocar los repositorios de datos maestros ni ningún componente de UI.
- Si en algún momento se decide centralizar también los datos maestros en un backend real, se sustituye la implementación de `src/data/repositories/*` por llamadas HTTP a una API, manteniendo exactamente las mismas firmas de función. El dominio (`src/domain/`) y las páginas de `src/features/` no requieren cambios.

## 6. Enrutado con hash (`#/admin/...`)

GitHub Pages no reescribe rutas en el servidor (no hay "SPA fallback" configurable como en otros hostings estáticos). Con `BrowserRouter`, recargar la página en `/admin/reglas` daría un 404 real servido por GitHub. `HashRouter` evita el problema por construcción: todo lo que va después de `#` lo resuelve el navegador sin ninguna petición al servidor.

Desde la introducción del borrador sin guardar en la ficha de unidad (ver 8quinquies) se usa `createHashRouter` + `<RouterProvider>` (data router) en vez del modo declarativo `<HashRouter><Routes>`: es el único modo de React Router v7 que soporta `useBlocker()`, necesario para interceptar la navegación cuando hay cambios sin guardar. `AppShell` pasó de recibir `children` a renderizar `<Outlet />`, que es como un data router inyecta la ruta activa dentro de un layout compartido.

## 8quinquies. Ficha de unidad como borrador: nada se guarda hasta pulsar "Guardar cambios"

Hasta ahora cada edición en la ficha de una unidad (marcar/quitar una regla, cambiar el nombre del Campeón, teclear una estadística...) escribía en la base de datos al instante. Eso hacía imposible "probar" una combinación y echarse atrás, y no avisaba de nada si se navegaba fuera con cambios a medias. Se ha sustituido por un modelo de **borrador local**:

- `UnitDetailPage` mantiene un objeto `UnitDraft` en estado de React (campos escalares, los tres conjuntos de relaciones N:M, los perfiles de montura/carro asignados, los nombres propios del grupo de mando y las estadísticas de las fichas editables) que se inicializa a partir de la unidad cargada y **no escribe nada en SQLite** mientras se edita.
- Un booleano `dirty` se activa en cuanto cualquier campo del borrador cambia, y se muestra como aviso junto al botón "Guardar cambios".
- "Guardar cambios" valida el formulario y, si es válido, llama a `UnitRepository.saveUnitDetail` — un único método que aplica TODOS los cambios pendientes (campos, relaciones, perfiles, nombres, estadísticas) y persiste una sola vez en IndexedDB, en vez de una escritura por cada toggle como antes. Las relaciones N:M se guardan "sustituyendo el conjunto completo" (borrar todo lo de la unidad + insertar lo seleccionado) porque el borrador ya tiene el conjunto final, no un diff.
- `EditableAttributeTable` pasó de gestionar su propio estado con guardado al perder el foco, a ser un componente controlado (`value`/`onChange`) — el dueño del estado es el borrador de la página, no la tabla.
- Única excepción: "+ Crear ficha base" (para una unidad recién creada sin ninguna ficha de atributos todavía) escribe al instante, porque no hay nada que "deshacer" — no existía ninguna fila que editar antes. Para no descartar el resto del borrador en curso, no dispara una recarga completa de la unidad: solo mete el perfil recién creado en un estado local aparte (`baseProfileOverride`) que sustituye a `unit.profiles.base` en el render hasta la próxima carga real.
- Al navegar fuera de la ficha con `dirty === true`, `useBlocker` intercepta la navegación (ver 6) y muestra `UnsavedChangesDialog` con tres opciones: guardar y salir, descartar y salir, o seguir editando. Para el caso de cerrar o recargar la pestaña del navegador (que `useBlocker` no cubre, al ser un evento del navegador y no de React Router) hay un listener de `beforeunload` como red de seguridad.

## 8sexies. Segunda pasada de tipografía: jerarquía cabecera/campo y cajas a la medida del dato

La primera pasada de estandarización (8quinquies y la anterior sobre tamaños) dejó cabeceras de caja en `text-base` (16px) y texto de campo en `text-sm` (14px) — una diferencia demasiado sutil, agravada porque la cabecera usa una fuente de display (`font-display`) cuyo cuerpo visual es más pequeño que el de la fuente de los campos al mismo tamaño en px. Se amplía el contraste:

- Cabeceras de caja/panel (`Panel` de `UnitDetailPage`, `Modal`, `EmptyState`, y las cabeceras de tarjeta de Facciones/Reglas/Monturas/Carros) pasan de `text-base` a `text-lg`.
- El texto de los campos (`TextField`, `TextArea`, `Select` — usados en toda la app, así que el cambio es automático en todos los formularios) y el de los elementos ya asignados en `RelationEditor` pasan de `text-sm` a `text-xs`.
- Los campos numéricos de "Datos generales" (coste, tamaño mínimo/máximo, T.S.) dejaron de ocupar el ancho completo de su columna: cada uno vive en una caja estrecha (`w-14` a `w-20`) dimensionada según el número de dígitos que puede tener de verdad (coste ≤ 999, tamaños ≤ 99, T.S. de un solo dígito 2-7), con esos mismos límites ahora validados en `domain/validation.ts` en vez de ser solo una convención visual.
- "Equipo (básico, siempre incluido)" pasó de `TextArea` (2 líneas) a `TextField` (una línea) — el texto real que se guarda ahí siempre ha cabido en una línea.
- "Notas internas" se quitó de la ficha visible (el campo no aportaba valor a la vista general y ocupaba espacio) pero la columna `units.notes` sigue existiendo intacta: `UnitDraft` la sigue cargando y reenviando tal cual en `saveUnitDetail`, simplemente no hay ningún control en pantalla que la edite. Si hace falta recuperarla, basta con volver a añadir el campo a la UI.

## 7. Estructura de carpetas

```
webapp/
  db/schema.sql              — Definición canónica del esquema (fuente de verdad del modelo)
  scripts/etl_datos_json.py  — Único proceso autorizado para generar public/data/warhammer.db
  public/data/warhammer.db   — Semilla de datos maestros (se versiona en git)
  src/
    domain/                  — Tipos y lógica de negocio pura (sin React, sin sql.js)
    data/
      sqlite/client.ts       — Único punto que sabe que la BBDD es SQLite/sql.js
      repositories/          — Una función por entidad; API que consume el resto de la app
    features/
      admin/                 — Facciones, Unidades, Reglas (CRUD)
      fichas/                — Generador de fichas (placeholder, próxima fase)
      ejercitos/             — Constructor de listas (placeholder, próxima fase)
    shared/
      ui/                    — Componentes de interfaz reutilizables (Button, Modal, TextField...)
      layout/                — AppShell, navegación, buscador global
      hooks/                 — useAsync y futuros hooks compartidos
    app/                     — Router y arranque de la aplicación
```

Cada módulo de `features/` solo importa de `domain/`, `data/repositories/` y `shared/`; nunca de otro módulo de `features/` directamente. Si dos módulos necesitan compartir algo, ese algo sube a `shared/` o `domain/`.

## 8bis. Identidad visual "de códex"

La primera versión usaba una paleta gris/ámbar genérica de SaaS. Se ha sustituido por un lenguaje visual que se acerca a los libros de ejército reales (fondo de pergamino `FONDO_HOJA.jpg`, tipografía Caslon Antique para títulos —la misma que ya usan las herramientas hermanas HojaEjercito y CodexMaker—, paleta de tierras/tinta/marrón-rojizo), definido centralmente en `src/index.css` (`@theme`) y en los componentes de `shared/ui/`. Cualquier pantalla nueva hereda el estilo automáticamente en cuanto usa esos componentes compartidos, sin tener que repetir colores sueltos.

La navegación pasó de una barra lateral a una barra horizontal superior (`shared/layout/TopNav.tsx`), dejando los márgenes izquierdo y derecho de la página libres — el contenido se centra en una columna tipo "página" (`max-w-4xl`) en vez de ocupar todo el ancho pegado a un sidebar.

El editor de relaciones N:M de una unidad (`features/admin/units/RelationEditor.tsx`) se rediseñó para que lo asignado se vea siempre primero y de un vistazo (con su descripción completa si la tiene, como las reglas especiales) y se pueda quitar con un clic, con un buscador aparte para añadir más — un único componente reutilizado para reglas, equipo, mejoras y perfiles de montura/carro, en vez de una lista de checkboxes genérica.

## 8ter. Emblemas de facción, nombres personalizados y confirmaciones de borrado

- **Emblema de facción con dos orígenes.** Sin servidor no hay dónde subir un fichero aparte, así que un emblema personalizado se guarda como `BLOB` (`factions.emblem_data` + `emblem_mime`) directamente en la base de datos, igual que cualquier otro dato editable. Si no hay emblema propio, se usa el de fábrica (`image_path`, una ilustración ya incluida en el repositorio y redimensionada por el ETL). `factionRepository.mapFaction` resuelve la URL final (`emblemUrl`) con ese orden de prioridad, así que la UI nunca decide entre las dos fuentes. "Borrar" solo vacía `emblem_data`/`emblem_mime`, con lo que la facción vuelve a mostrar su emblema de fábrica en vez de quedarse sin ninguno.
- **Redimensionado en el navegador antes de guardar.** Como cada escritura reexporta la base de datos entera (ver punto 3), subir una foto de varios MB tal cual sería lento y haría crecer mucho la copia en IndexedDB. `shared/image.ts` redimensiona a un máximo de 480px de lado y recomprime a JPEG calidad 0.82 con un `<canvas>` antes de llamar a `FactionRepository.setEmblem`, con el mismo criterio que usa el ETL para los emblemas de fábrica.
- **Nombre personalizado del Campeón.** `unit_command_options.custom_name` permite que una unidad concreta llame a su Campeón de otra forma (p.ej. "Herrero rúnico"); `NULL` usa el nombre por defecto "Campeón" en toda ficha. Solo se expone edición para el rol `CAMPEON` — Músico y Portaestandarte siguen usando el nombre del catálogo (`command_roles.name`), que es lo que se pidió por ahora.
- **Icono de papelera para borrar.** Se sustituyó el símbolo "✕" por un icono de papelera (`shared/ui/icons.tsx#TrashIcon`, SVG en línea sin dependencias) en todos los sitios donde se borra algo: facciones, reglas especiales del catálogo y elementos asignados a una unidad (`RelationEditor`). La "✕" de cerrar un modal se mantiene, porque esa no es una acción destructiva.
- **Confirmación al quitar una regla especial de una unidad.** `RelationEditor` acepta una prop `confirmRemove`; cuando está activa (solo se usa para las reglas especiales de una unidad, no para equipo/mejoras/perfiles, que son más reversibles y de menor impacto), quitar un elemento abre un `ConfirmDialog` en vez de aplicar el cambio al instante.

## 8quater. Monturas y Carros como catálogos con facción asociada, categorías nuevas, y ficha propia del Campeón

- **Monturas y Carros ahora son catálogos de Administración por derecho propio** (`/admin/monturas`, `/admin/carros`), no solo perfiles "reutilizables" sueltos. `attribute_profiles` ganó una columna `profile_kind` (`'unidad' | 'montura' | 'carro'`) que sustituye la deducción implícita que había antes (perfil con `name` = reutilizable). Una tabla nueva, `profile_factions` (N:M), dice qué facción o facciones pueden usar cada montura/carro; el ETL la rellena automáticamente a partir de qué unidades de qué facción ya usaban cada perfil en el origen, y desde Administración se puede añadir o quitar cualquier asociación. La ficha de una unidad (`UnitDetailPage`) solo ofrece para añadir las monturas/carros asociados a su propia facción — es la propia consulta (`listForFaction`) la que filtra, no un chequeo a posteriori en la UI.
- `MountRepository` y `ChariotRepository` (`profileCatalogRepository.ts`) son la misma fábrica de repositorio parametrizada en `profile_kind`, porque ambos catálogos tienen exactamente la misma forma (ficha de 9 atributos + facciones asociadas) — evita duplicar el CRUD dos veces. Lo mismo en la UI: `ProfileCatalogListPage`/`ProfileCatalogFormModal` son genéricos, y `MountsListPage`/`ChariotsListPage` son envoltorios de una línea que solo fijan las etiquetas y el repositorio.
- **Categorías nuevas**: además de Básicas/Especiales/Singulares, ahora existe "Personajes" (vacía por ahora, para fichas de personaje sueltas que se irán añadiendo desde Administración). Ver 8octies para las categorías "Asedio" y "Bestia" añadidas después.
- **Ficha propia del Campeón**: `unit_command_options` ganó `profile_id` (referencia a `attribute_profiles`, kind `'unidad'`). El ETL genera automáticamente la ficha de cada Campeón como el perfil base de su unidad con +1 en Ataques (`bump_attacks`); si la característica de Ataques del perfil base no es un entero simple (dados, "-", "E"...) se deja igual al perfil base sin sumar, y la unidad queda listada en el aviso final de la importación para revisión manual. Es editable por unidad desde `UnitDetailPage` (tabla de atributos con inputs, igual que el resto de perfiles pero editable).
- **Equipo básico y T.S.**: `units` ganó `equipment_text` (texto libre: el equipo que la unidad siempre lleva) y `armor_save` (número: tirada de salvación por armadura). Ninguno de los dos existe en el origen, así que ambos quedan vacíos tras la importación y se rellenan a mano desde Administración — mismo tratamiento que `min_size`.
- **"Montura/Dotación" y `equippable_by_character`**: la etiqueta de esta sección en la ficha de unidad pasó de "Perfil de montura" a "Montura/Dotación" (el propio origen ya llama así al campo, `MONTURA_DOTACION`). `attribute_profiles` ganó una columna `equippable_by_character` (booleano, default `false`) que solo tiene sentido para `profile_kind = 'montura'`: si un personaje puede equiparse esa montura/dotación individualmente, no solo una unidad completa. Se edita desde Administración > Monturas (`ProfileCatalogFormModal`, prop `showEquippableByCharacter` — el catálogo de Carros no la recibe, así que ese formulario no muestra el campo). Todo lo importado queda a `false`; se marca caso por caso a mano.

## 8septies. "Ejércitos": constructor de listas, modernizando el Hoja de Ejército original

El proyecto partió de una herramienta previa, standalone (`HojaEjercito/index.html` + `script.js`, ~1650 líneas): un formulario con desplegables de Tropa/Equipo/Opciones, casillas P/M/C (Portaestandarte/Músico/Campeón), una tabla de la lista con el total de puntos, guardado/carga como fichero `.json` a mano, y export a PDF con textura de pergamino y tipografía propia (jsPDF dibujado a mano, con cabeceras/filetes decorativos por página). El nuevo módulo `/ejercitos` reconstruye esa misma experiencia sobre la Administración y el motor de reglas ya existentes, con las siguientes decisiones (consultadas expresamente con el usuario antes de construir, dada la envergadura del cambio):

- **Validación activa, no solo un totalizador.** El original no comprobaba nada (mínimos/máximos, unicidad, equipo incompatible...); la ficha de unidad ya modela todas esas reglas, así que el constructor las aplica: `domain/armyValidation.ts#validateEntryInput` bloquea (no dispara error hasta que se corrige) tamaño fuera de min/max, equipo incompatible entre sí (`equipment_incompatibilities`, generada automáticamente en el ETL — ver punto 4 — y hasta ahora sin ningún consumidor) y una unidad marcada `is_unique` repetida. `validateList` añade el único aviso de nivel de lista que NO bloquea: superar el límite de puntos (se decidió expresamente que solo avise, no bloquee). Ver 8octies sobre el campo "obligatoria" que existió brevemente aquí y se eliminó por redundante.
- **Equipo y opciones múltiples por entrada**, a diferencia del original (un único desplegable de cada). Cada entrada de la lista (`army_list_entries`) tiene sus propias tablas de unión `army_list_entry_equipment`/`army_list_entry_upgrades`, igual de forma que `unit_equipment_options`/`unit_upgrade_options` en la ficha maestra — se puede marcar varias piezas sueltas a la vez respetando las incompatibilidades.
- **Listas guardadas en la propia app** (`army_lists`, tabla nueva) en vez de descargar/subir un `.json` a mano: "Mis ejércitos" (`ArmyListsPage`) lista, crea, renombra y borra listas, todas persistentes en la misma IndexedDB que el resto de la app (ver punto 3). No hay "usuarios" todavía, así que de momento todas las listas guardadas son visibles para quien abra la app, igual que los datos de Administración.
- **Límite de puntos editable por lista** (`army_lists.points_limit`, `NULL` = sin límite) — el original no tenía ninguno. Si se supera, `validateList` lo señala como aviso (no bloquea): puede haber partidas o casas de reglas donde pasarse un poco sea aceptable.
- **Monturas/carros sin coste propio**: si una unidad tiene más de una montura o carro disponible en su ficha, `army_list_entries.mount_profile_id`/`chariot_profile_id` registra cuál se ha elegido (solo para mostrarla correctamente), pero no suma coste aparte — igual que el original, donde el coste de la montura ya iba incluido en el coste base de la unidad que la llevaba.
- **Fórmula de coste** (`computeEntryCost`) es la misma que la del original, generalizada de un único equipo/opción a conjuntos: `cantidad × (coste_base + Σ equipo elegido) + Σ opciones de unidad + coste de cada rol de mando marcado`. El equipo se multiplica por miniatura porque son piezas físicas (armas, armaduras); las opciones de unidad y el grupo de mando se suman una sola vez porque son un único añadido a la entrada completa, no por miniatura.
- **PDF con el mismo aspecto**, no reconstruido desde cero: se reutilizan literalmente los ficheros del original — la textura `ico/FONDO_HOJA.jpg` y la tipografía `CaslonAntique-Regular/Bold.ttf` — copiados a `public/assets/army-sheet/`. Lo que sí se simplificó fue el CÓMO se dibuja: el original construía la tabla y las cabeceras a mano con primitivas de jsPDF (~600 líneas, con lógica propia de continuación de página, filetes decorativos, etc.); la versión nueva (`features/army-lists/exportArmyListPdf.ts`) usa `jspdf-autotable` para la tabla de unidades y dibuja el fondo de pergamino en cada página vía el hook `willDrawPage` (ver 8nonies sobre por qué no `didDrawPage`), con un resumen de reglas especiales al final — mismo resultado reconocible, bastante menos código que mantener. `jsPDF`/`jspdf-autotable` se cargan con `import()` dinámico solo al pulsar "Exportar PDF" (van en su propio chunk, ~430KB) para no engordar el bundle inicial de toda la app con una librería que la mayoría de sesiones no llega a usar.
- **Panel derecho con ficha y reglas**, igual que el original: al elegir una unidad en el formulario de "Añadir unidad" se ve su ficha de atributos (base + montura/carro) y sus reglas especiales con descripción completa, reutilizando `AttributeTable` (el mismo componente que ya usa `UnitDetailPage` y los catálogos de Monturas/Carros — ver punto 8quater).

## 8octies. Eliminación de `is_mandatory` y categorías "Asedio"/"Bestia" (fin de la categoría "(-)")

- **`units.is_mandatory` eliminado por completo** (esquema, ETL, dominio, repositorio y UI). Se consideró redundante: en la práctica ninguna facción del origen tenía unidades realmente "obligatorias en toda lista" de forma consistente, y el propio usuario pidió quitarlo tanto de BBDD como de frontend. Se quitó la columna de `db/schema.sql`, el `SET is_mandatory = ?` de los dos `UPDATE` de `unitRepository.ts` (`updateScalarFields` y el guardado batch `saveUnitDetail`), el campo `isMandatory` de `Unit`/`UnitScalarInput`, la casilla "Obligatoria en toda lista de la facción" de `UnitDetailPage`, el badge "Obligatoria" de `UnitsListPage`, y el aviso correspondiente de `domain/armyValidation.ts#validateList` (que ahora solo recibe `entries` y `pointsLimit`, sin la lista de unidades obligatorias).
- **Fin de la categoría "(-)" (antes `SIN_CATEGORIA`)**: las 33 unidades que habían quedado ahí por no tener categoría estándar en el origen se repartieron en tres grupos:
  - **17 unidades de la facción "Bestias"** (monstruos sueltos: Dragón, Grifo, Hidra, Manticora...) → nueva categoría **"Bestia"** (`BESTIA`). Importante: "Bestias" es una facción distinta de "Hombres Bestia" (facción normal, ya categorizada de origen) — se usó comparación exacta de nombre de facción (mismo `title_es(clean_name(...))` que inserta la tabla `factions`), no una coincidencia parcial, para no tocar por error las unidades de Hombres Bestia.
  - **8 unidades de la facción "Asedio"** (Ariete, Torre de asedio, Escalas, Manteletes...) → nueva categoría **"Asedio"** (`ASEDIO`).
  - **8 unidades sueltas de otras facciones**, reasignadas a mano una a una según lo indicado por el usuario: Enjambre de duendes y Lobos salvajes (Elfos Silvanos) → Básica; Buscamuerte (Enanos) → Especial; Esclavista (Enanos del Caos) y Señor de las alimañas (Skaven) → Personaje; Mastines de Khorne (Hordas del Caos), Lobos gigantes y Mastines (Norsca) → Básica.
  - Con los tres grupos (8 + 17 + 8 = 33) la categoría "(-)" queda vacía y se eliminó del catálogo `unit_categories`; el ETL (`scripts/etl_datos_json.py`) resuelve la categoría de cada unidad con esta prioridad: reasignación manual por nombre+facción → categoría de la facción (Asedio/Bestias) → código de tipo B/E/S del origen. Lleva un chequeo defensivo (`unresolved_category_units`) que avisaría si alguna unidad quedara sin categoría — verificado tras la regeneración que la lista está vacía (0 unidades con `category_id NULL`, 6 categorías en total, ninguna "(-)" ni `SIN_CATEGORIA`).
- `SCHEMA_VERSION`/`EXPECTED_SCHEMA_VERSION` subidos a `1.6.0` por el cambio de columna y de catálogo de categorías.

## 8nonies. Ronda de correcciones sobre "Ejércitos": multi-facción, Campeón, PDF, selector de unidad

Correcciones pedidas tras el primer uso real del constructor de listas (ver 8septies). Sin cambios de esquema — todo a nivel de repositorio/dominio/UI.

- **Listas multi-facción.** `army_lists.faction_id` sigue existiendo (ahora es la "facción principal": solo decide el nombre por defecto y la cabecera del PDF), pero el navegador de "Añadir unidad" ya no filtra por `list.factionId` — `UnitRepository.listAll()` (nuevo método) trae las unidades de TODAS las facciones, y un selector de facción dentro del propio panel decide qué subconjunto se explora en cada momento. Se puede añadir a una misma lista una unidad de Bretonia y otra de Skaven sin ningún aviso ni bloqueo: el dominio (`armyValidation.ts`) nunca comprobó "misma facción", así que no hacía falta tocarlo. `ArmyListFormModal` renombra la etiqueta a "Facción principal" y añade una nota aclarando que luego se puede mezclar.
- **Nombre del Campeón ya no es editable.** El campo de texto libre "Nombre del Campeón (opcional)" se quitó de `ArmyListBuilderPage`; ahora se limita a mostrar, junto a la casilla, el nombre ya definido en la ficha de la unidad (`commandOptions.find(role===CAMPEON).customName ?? role.name`) — exactamente lo que ya documentaba el comentario de `army_list_entries.champion_name` en el esquema ("NULL = usa el nombre propio/genérico ya definido en la ficha de la unidad"). `handleSaveEntry` ahora graba `championName: null` siempre; `EntryDraft` perdió el campo `championName` del todo.
- **Bug del PDF en blanco, corregido.** El PDF exportado salía con la textura de pergamino y nada más — ni cabecera ni tabla. Causa: el hook `didDrawPage` de `jspdf-autotable` (que repinta el fondo en cada página) se dispara DESPUÉS de que esa página dibuje su contenido, así que el fondo tapaba por completo lo que `autoTable` acababa de dibujar (confirmado renderizando el PDF a PNG con `pdftoppm` antes y después del fix). Arreglado cambiando a `willDrawPage` (se dispara ANTES del contenido de esa página) y, además, saltándose la página 1 (`data.pageNumber > 1`) porque su fondo + cabecera ya se pintan a mano antes de llamar a `autoTable` — repintarlo ahí habría vuelto a tapar esa cabecera. Verificado con una prueba de una página y otra forzando paginación a varias páginas.
- **Selector de "Añadir unidad" rediseñado.** El desplegable único `<Select>` con `<optgroup>` por categoría se sustituyó por: selector de facción + buscador de texto, una fila de pestañas por categoría (estilo píldora, activa en marrón) y, debajo, la lista de unidades de esa categoría como tarjetas plegables — cada tarjeta muestra nombre y coste, y al pulsarla despliega el mismo formulario de opciones (cantidad, equipo, montura/carro, grupo de mando, botón Añadir) que antes vivía siempre visible bajo el desplegable. Solo una tarjeta puede estar desplegada a la vez (reutiliza el mismo estado `selectedUnit`/`draft` de antes, ahora disparado por el click de la tarjeta en vez del `onChange` del select). Editar una entrada ya añadida sigue abriendo un panel "Editar entrada" separado y compacto (sin el navegador de categorías, porque la unidad ya está fija).
- **Cantidad de miniaturas robusta.** El campo "Cantidad" pasó de `min={selectedUnit?.minSize ?? 1}` a `min={0}` fijo, con un `onChange` que nunca deja `NaN` ni el campo vacío (`raw === '' ? 0 : Number(raw)`, con `Math.max(0, …)`). El mínimo real de la unidad lo sigue exigiendo `domain/armyValidation.ts#validateEntryInput` como error bloqueante (mensaje "el tamaño mínimo es N"), no el atributo HTML `min` del input — así el usuario siempre ve un número, nunca un campo en blanco o inválido, y el error de validación es explícito en vez de un bloqueo silencioso del navegador.

## 8undecies. Segunda ronda: clamp de cantidad, equipo incompatible visible en el buscador, P/M/C en línea

- **Cantidad: clamp automático al máximo.** El `onChange` del campo "Cantidad" ahora recorta directamente al `maxSize` de la unidad si se escribe un número mayor, en vez de dejar un valor imposible que solo se rechazaría al guardar.
- **Equipo incompatible, deshabilitado en el propio buscador.** Se investigó a fondo el caso reportado (Pavesiers con Alabarda + Lanza a la vez): la tabla `equipment_incompatibilities` y `domain/armyValidation.ts#validateEntryInput` YA marcaban ese par como excluyente y bloqueaban el guardado — verificado repitiendo la consulta y la validación directamente contra `warhammer.db` con Node. El problema real era de UX: el buscador de equipo dejaba seleccionar libremente cualquier pieza y el conflicto solo se descubría (con un mensaje de error) al pulsar "Añadir a la lista", así que era fácil dejar una entrada a medio completar con dos piezas del mismo hueco. `shared/ui/RelationEditor.tsx` ganó una prop opcional `getDisabledReason(item)`: si devuelve texto, esa sugerencia sale deshabilitada en el buscador con el motivo entre paréntesis (p. ej. "Lanza (Incompatible con Alabarda)") en vez de poder añadirse — no afecta a los demás usos de `RelationEditor` (reglas especiales, opciones de unidad, equipo en Administración) porque la prop es opcional y solo `ArmyListBuilderPage` la rellena, con una función `equipmentDisabledReason` que recorre los pares de `incompatiblePairs` contra lo ya elegido en el borrador.
- **Grupo de mando en una sola línea.** El contenedor de las casillas Portaestandarte/Músico/Campeón pasó de `flex flex-wrap` a `flex flex-nowrap overflow-x-auto`, y cada `<label>` ganó `shrink-0 whitespace-nowrap`, así que las tres opciones se mantienen siempre en la misma línea (con scroll horizontal solo si el panel fuera realmente estrecho) en vez de partirse en varias líneas cuando el nombre del Campeón alarga esa tercera etiqueta.

## 8duodecies. Etiqueta del Campeón sin prefijo duplicado + `default_size` (tamaño real del origen)

- **"Campeón — Campeón" corregido.** `campeonName` cae de vuelta a `role.name` ("Campeón") cuando la unidad no tiene un nombre propio puesto en su ficha, así que anteponer siempre el literal "Campeón — " producía "Campeón — Campeón" para la inmensa mayoría de unidades (solo las que tienen un nombre propio distinto se libraban). Se quita el prefijo: la casilla ahora muestra directamente `{campeonName ?? 'Campeón'}` (+coste), igual de informativo y sin la repetición.
- **`units.max_size` estaba mal derivado del origen — no era un máximo.** Investigando el reporte de "tamaños incorrectos" se revisó `HojaEjercito/script.js` (la herramienta original) línea a línea: el campo `NUMERO` de `datos.json` NUNCA fue un límite máximo de la unidad — el propio código fuente lo etiqueta con el comentario `🔥 AUTOCOMPLETAR NÚMERO` y solo lo usa para **precargar** el campo "número" del formulario al elegir la tropa; el jugador podía escribir cualquier otra cantidad después sin ninguna restricción. El ETL (`scripts/etl_datos_json.py`) mapeaba erróneamente `NUMERO → max_size`, lo que hacía que `domain/armyValidation.ts#validateEntryInput` bloqueara cantidades por encima de ese número aunque la unidad real no tuviera ese límite (p. ej. Guerreros enanos quedaba tope en 24 solo porque esa era la cantidad "de partida" sugerida en la hoja original, no un máximo de la unidad).
- **Solución: columna nueva `units.default_size`**, separada de `min_size`/`max_size` (que siguen siendo límites de validación, ahora `NULL` para las 439 unidades tal como ya estaba documentado en "Deuda conocida" — sin datos reales de límites en el origen, hay que rellenarlos a mano desde Administración si se conocen). `default_size` se rellena con `NUMERO` y solo se usa para precargar la "Cantidad" al elegir una unidad en el constructor de listas (`ArmyListBuilderPage#handlePickUnit`: `quantity: detail.defaultSize ?? detail.minSize ?? 1`) — nunca bloquea nada. Editable desde Administración > Unidades ("Tam. def.", junto a Tam. mín./Tam. máx./T.S.). `SCHEMA_VERSION`/`EXPECTED_SCHEMA_VERSION` subidos a `1.7.0`.

## 8decies. Etiqueta única por unidad (exportación puntual a Excel, no en la app)

A petición del usuario, se generó un Excel (`etiquetas_unidades.xlsx`, entregado directamente, no versionado en el repo) con una etiqueta única por unidad de las 439 totales, elegida entre: Personaje, Bestia, Asedio, Infantería, Proyectiles, Máquina de guerra, Carros, Caballería, Caballería Ligera, Caballería monstruosa, Criatura, Monstruo, Unidad Voladora. ## 8terdecies. Backend compartido (Cloudflare Worker + D1) y optimización de rendimiento

**De sql.js/IndexedDB local a una D1 real compartida.** El usuario pidió que los cambios hechos por un usuario (facciones, unidades, listas de ejército...) se vieran reflejados para los demás — algo que la copia de sql.js en IndexedDB de cada navegador (ver punto 3) no podía hacer por diseño, al vivir enteramente en el dispositivo de quien la edita. Tras comparar alternativas con el usuario (Turso, Docker+VPS/Fly.io/Railway, Cloudflare Workers+D1), se eligió **Cloudflare D1** (SQLite gestionado) porque reutiliza `db/schema.sql` casi sin cambios, más un **Worker** (`webapp/worker/`) que expone tres rutas:

- `POST /query` — cualquier `SELECT`/`WITH`, público, sin contraseña (los datos de catálogo son de solo lectura para cualquier visitante, igual que ya lo eran al estar todos en el mismo bundle estático).
- `POST /mutate` — un batch de `INSERT`/`UPDATE`/`DELETE` ejecutado atómicamente vía `env.DB.batch(...)`, protegido por una **contraseña de grupo compartida** (no hay usuarios/cuentas individuales: es una herramienta de un grupo cerrado de jugadores). El Worker solo compara el hash SHA-256 recibido contra un secreto (`GROUP_PASSWORD_HASH`, fijado con `wrangler secret put`, nunca en el código ni en D1); el cliente (`data/network/auth.ts`) guarda ese hash en `localStorage` tras pedirlo una vez (`PasswordGate`, delante de Administración y del constructor de listas — la navegación de solo lectura no lo pide).
- `POST /admin/reset-seed` — mismo gate de contraseña; borra las tablas maestras y las repone desde `worker/src/seed-data.ts` (un dump congelado de `warhammer.db` en el momento de la migración), sustituyendo al antiguo "vuelve a clonar la semilla de IndexedDB".

Ambas rutas de escritura validan que el SQL empiece por el verbo esperado (whitelist de prefijo) antes de ejecutarlo — es la única barrera real contra un cliente comprometido, dado que no hay ORM ni sentencias predefinidas en el servidor; se documentó explícitamente en el propio Worker que esto es "deliberadamente simple" para el nivel de confianza de un grupo de juego, no un producto multiusuario público.

Los BLOB (de momento solo `factions.emblem_data`) viajan como `{ __b64: string }` dentro del JSON en ambas direcciones — ni D1 sobre HTTP ni `fetch`/JSON aceptan `Uint8Array` nativo — codificados/decodificados de forma simétrica en `client.ts` y en el Worker.

**Hosting partido**: GitHub Pages sigue sirviendo solo el frontend estático (sin cambios en ese flujo); el Worker se despliega aparte con `wrangler deploy` desde `webapp/worker/` (fuera del alcance de las herramientas de Cloudflare disponibles en este entorno, que solo permiten crear/consultar D1 y Workers, no desplegar código ni fijar secretos — esos pasos los hace el usuario a mano). La URL resultante se pasa al build de GitHub Actions como variable de repositorio `VITE_API_BASE_URL` (`.github/workflows/deploy.yml`), y en local vive en `webapp/.env.local` (gitignored).

**Botón "Restaurar datos"** cambia de alcance: antes solo afectaba al navegador de quien lo pulsaba; ahora borra y repone los datos maestros **para todo el mundo** (mismo aviso reforzado en `ResetDataButton`).

**Rendimiento tras la migración — caché local por repositorio.** El primer efecto notado por el usuario tras el cambio fue que la app iba mucho más lenta: cada `query`/`exec` ahora es un `fetch` real con latencia de red, y una auditoría reveló un problema serio de sobre-consulta, no solo latencia por-petición:

- `armyListRepository.ts#resolveEntry` reconstruía la ficha completa de la unidad (`UnitRepository.getDetailById`, 7 queries) por CADA entrada de la lista, y esas 7 queries se lanzaban secuencialmente (`await` una detrás de otra) en vez de en paralelo. Abrir el constructor de listas con 5 entradas ya guardadas suponía **~56 peticiones HTTP**; añadir una unidad más, otras ~60.
- El catálogo (facciones, unidades, categorías, reglas especiales, equipo, mejoras, roles de mando, monturas/carros) se volvía a pedir entero en cada visita a una página, aunque el usuario confirmó que **ese catálogo casi nunca cambia** — a diferencia de las listas de ejército, que sí se crean/editan constantemente.

**Segunda ronda — la D1 vive en Norteamérica y el usuario prueba desde España.** Tras la caché, la app seguía notándose lenta sobre todo en la primera carga (antes de calentar la caché). Causa adicional: la D1 se creó sin especificar región (`primary_location_hint`) y Cloudflare la ubicó en Norteamérica-Este (ENAM); cada peticion cruza el Atlántico. D1 no permite cambiar la región de una base ya creada (ni con `jurisdiction` ni con `primary_location_hint`, ambos solo se fijan al crearla) — recrearla habría significado volver a migrar todos los datos y desplegar de nuevo. En su lugar se activó **D1 Read Replication** (función nativa de Cloudflare, gratuita, sin migrar nada): el Worker pasó de usar `env.DB` directamente a `env.DB.withSession(bookmark)` en las tres rutas, y Cloudflare crea automáticamente réplicas de solo lectura en varias regiones, encaminando cada sesión a la más cercana. El "bookmark" que identifica hasta qué punto ha visto la base de datos cada sesión viaja en la cabecera `X-D1-Bookmark` (Worker → cliente tras cada respuesta, cliente → Worker en la siguiente petición, guardado en memoria en `client.ts`), para que una lectura justo después de una escritura propia siempre la vea aunque la sirva una réplica distinta a la del primario. Activar la réplica en sí es una acción de un clic en el panel de Cloudflare (D1 > `wharmy-db` > Settings > Enable Read Replication) que no está disponible por API/MCP en este entorno, así que la hace el usuario a mano.

Solución de caché, sin tocar el Worker ni `client.ts`: cada repositorio de catálogo (`factionRepository`, `lookupRepositories`, `ruleRepository`, `profileCatalogRepository`, `unitRepository`) mantiene su **propia caché en memoria** (una variable de módulo o `Map`, no un bus global), invalidada ÚNICAMENTE dentro de sus propios métodos de escritura y siempre DESPUÉS de que la escritura remota se confirme con éxito (si `exec`/`execBatch` lanza por un fallo de red o un 401, la función corta antes de llegar a invalidar — la caché nunca queda en un estado a medias). Deliberadamente NO se usa el bus `onDatabaseChange` de `client.ts` para esto: ese se dispara con CUALQUIER escritura, incluida cada vez que se guarda una entrada de lista de ejército, y habría vaciado el caché del catálogo constantemente sin necesidad (las listas de ejército en sí — `army_lists`/`army_list_entries` — no se cachean, cambian todo el rato). `unitRepository.getDetailById` además paraleliza sus 7 queries con `Promise.all` en dos tandas (las que solo dependen del `id` de la unidad; luego facción/categoría, que dependen del resultado de la primera) para que incluso un cache-miss sea rápido. Con el catálogo y las fichas de unidad ya calientes en caché de una visita anterior, el mismo escenario de 5 entradas pasa de ~56 peticiones a ~13 (quedan solo las que sí cambian todo el rato: la lista, sus filas de entrada, y el equipo/mejoras elegidos por cada entrada).

**Tercera ronda — el catálogo entero en memoria (sql.js) en vez de por red.** Incluso con caché y con Read Replication, el usuario seguía notando lentitud (sobre todo en la primera carga de cada página, cuando la caché de ese repositorio en concreto todavía está fría). Propuesta del propio usuario: ya que el catálogo es pequeño y casi nunca cambia, cargarlo entero en memoria al abrir la app, igual que en la arquitectura original de un solo sql.js — pero sin renunciar a que sea D1 la fuente de verdad compartida. Implementado como:

- Nueva ruta `GET /snapshot` en el Worker (pública, sin contraseña, igual que `/query`): vuelca en paralelo (`Promise.all`) las 18 tablas de catálogo (`SNAPSHOT_TABLES` en `worker/src/index.ts` — deliberadamente NO incluye `army_lists`/`army_list_entries`/`army_list_entry_equipment`/`army_list_entry_upgrades`, que siguen siendo 100% de red) como un único JSON `{ [tabla]: filas[] }`, reutilizando la misma codificación `{__b64}` de los BLOB que ya usaban `/query`/`/mutate`.
- Nuevo módulo `data/sqlite/localCatalog.ts`: al primer uso (o al arrancar, vía `preloadLocalCatalog()` desde `DatabaseGate.tsx`, en paralelo con el chequeo de salud de la API) pide ese snapshot y construye una base de datos **sql.js** en memoria — reutilizando `db/schema.sql` (importado con el sufijo `?raw` de Vite, que lo embebe como texto en el bundle) para el DDL, y el `sql-wasm.wasm` que ya quedaba en `public/` desde antes de la primera migración. Esta copia vive solo en la pestaña (no se persiste en IndexedDB); recargar la página la reconstruye desde cero.
- Los 5 repositorios de catálogo pasaron sus lecturas de `query`/`queryOne` (red) a `queryLocal`/`queryLocalOne` (síncronas contra sql.js en memoria, sin latencia) — y con esto, las cachés manuales por repositorio de la ronda anterior (`listAllCache`, `detailByIdCache`) quedaron redundantes y se eliminaron: no tiene sentido cachear una lectura que ya es instantánea contra memoria local.
- Sus escrituras pasaron de `exec`/`execBatch` a `execCatalog`/`execCatalogBatch` (nuevas en `client.ts`): hacen exactamente la misma escritura de red que antes (D1 sigue siendo la fuente de verdad), y ADEMÁS replican las mismas sentencias sobre la copia local (`applyLocalWrite`), para que el propio navegador que edita vea su cambio reflejado al instante sin esperar a una recarga. "Restaurar datos de fábrica" (`resetToSeed`) no pasa por ahí (reescribe el catálogo entero sin sentencias individuales que replicar), así que en su lugar invalida la copia local entera (`invalidateLocalCatalog()`) y deja que la próxima lectura pida un snapshot fresco.
- `armyListRepository.ts` no se tocó: sigue siendo 100% de red con `query`/`queryOne`/`exec`/`execBatch`, tal como pide el propio catálogo de cambios rápidos (listas de ejército sí cambian todo el rato). Sus llamadas a `UnitRepository.getDetailById` se benefician igualmente de la velocidad del catálogo local sin ningún cambio en este fichero.

Con esto, la única latencia de red real que queda en el día a día es la propia de las listas de ejército (que sí cambian constantemente) y la carga inicial del snapshot (una vez por sesión, en paralelo con el resto del arranque).

## 8septendecies. Fichas: ancho real, exportación completa (Word/Hoja de referencia) y arreglo del menú Editor

Ronda de correcciones sobre 8sexdecies, a partir de feedback directo del usuario tras probar la sección: "se ve todo muy comprimido", "la exportación a PNG no funciona", "quiero los mismos formatos que el original" y "en Editor no se ven bien las secciones".

- **Compresión visual de la ficha.** La causa real no era de tipografía sino de ANCHO: `AppShell` centra todo el contenido de la app en `max-w-4xl` (896px), y la tarjeta de ficha (760px) más los dos paneles laterales (300px cada uno) necesitan bastante más que eso — la columna central del grid se quedaba en ~250px reales y la tarjeta se encogía a la fuerza (`maxWidth:100%`), apretando todo su contenido. Arreglado envolviendo la sección de Fichas en un wrapper "breakout" (`relative left-1/2 w-screen -translate-x-1/2`, con su propio `max-w-[1500px]` dentro) que escapa del límite de `AppShell` — técnica local, sin tocar el ancho global de la app (que sí conviene mantener para el resto de pantallas). Aprovechando el rediseño, la tarjeta también creció (760→780px) y se aumentaron tamaños de letra/márgenes internos (`UnitSheetCard.tsx`) para que se vea más "de mesa" y menos apretada, más parecida en espíritu al original.
- **Menú "Editor" recortado.** La barra de navegación (`TopNav.tsx`) tiene `overflow-x-auto` para poder desplazarse en pantallas estrechas; eso hace que CUALQUIER hijo con overflow vertical —incluido el desplegable "Editor", que era un simple `position:absolute`— quede recortado por ese mismo contenedor (overflow-x distinto de `visible` implica que overflow-y también deja de ser `visible`). Arreglado moviendo el panel del desplegable a un portal (`createPortal` a `document.body`, igual que `Modal.tsx`), posicionado a mano con `getBoundingClientRect()` del botón (recalculado en resize/scroll) — así escapa del recorte por completo.
- **La exportación a PNG no funcionaba: html2canvas 1.4.1 + Tailwind v4.** html2canvas no sabe interpretar las funciones de color modernas que genera Tailwind v4 (`oklch()` de la paleta por defecto, `color-mix()` de los modificadores de opacidad tipo `/40`) y aborta la captura entera al toparse con una — CodexMaker no tenía este problema porque su CSS está escrito a mano con hex/rgba planos. Arreglado con el workaround estándar para esta combinación: en el `onclone` de html2canvas se recorre el árbol clonado y se copia, como estilo INLINE, el valor YA RESUELTO de `getComputedStyle()` del elemento original (el navegador siempre lo da en rgb()/rgba(), nunca la función sin resolver) — ver `html2canvasColorFix.ts#copyResolvedColors`. Además, ni html2canvas ni un documento Word interpretan el `filter:brightness()`/`transform:scaleX(-1)` que se usan en pantalla para la ilustración: antes de exportar se "hornean" en los píxeles reales (`imageProcessing.ts#bakeIllustration`, mismo algoritmo que `adjustImageBrightness`/`flipImageHorizontal` de CodexMaker) y el blanco-y-negro de Vista se aplica al canvas ya capturado (`grayscaleCanvasInPlace`), replicando exactamente el pipeline de `captureSheetCanvas` del original.
- **Exportación completa a los 4 formatos.** `exportPng.tsx` (con zip vía `jszip` cuando se seleccionan varias fichas, igual que el original), y `exportWord.ts` con "Word con texto" (párrafos/tablas de Word de verdad, editables — mismo truco que CodexMaker: un HTML con namespaces `mso-*` servido como `application/msword`), "Word con imágenes" (cada ficha capturada e incrustada como imagen) y "Hoja de referencia" (tabla compacta Personajes/Unidades, una fila por perfil con las reglas especiales en una columna con `rowspan`). El salto de página se fuerza solo cuando una ficha no cabría en el hueco que queda de la página actual (mismo algoritmo de bin-packing que el original, `computeForcedPageBreaks`, midiendo el alto real renderizado). Deliberadamente NO se replicó la función de CodexMaker de "adjuntar un libro existente" (.doc/.docx) para insertar las fichas dentro — no encaja en el modelo de datos de WHArmy (aquí no hay ningún documento "adjuntado", las fichas siempre nacen del catálogo); cada exportación genera siempre un documento nuevo, que es el camino por defecto del programa original. Vista (color/blanco y negro) y Marco se aplican tal cual a TODAS las exportaciones (se exporta lo que se ve, igual que CodexMaker), no solo a la vista previa.
- **Iconos.** Los controles de Fichas (Ilustración, Escudo, Voltear, Restablecer, Vista, Marco, ocultar/mostrar completadas, exportar) pasaron de texto plano a icono+texto, con SVG nuevos en `shared/ui/icons.tsx` (mismo lenguaje visual que `TrashIcon`/`ChevronDownIcon`/`StarIcon` ya existentes — sin emojis, a diferencia de CodexMaker, para mantener la coherencia con el resto de la app).
- **Aviso de verificación:** este entorno de trabajo no tiene un navegador con interfaz gráfica disponible (sandbox sin permisos de root para instalar las dependencias de sistema de Chromium/Playwright), así que estos cambios se verificaron con `tsc -b` + `vite build` limpios y una revisión manual cuidadosa del código, pero NO se han podido probar de forma interactiva en un navegador real. Conviene que el usuario pruebe en persona, sobre todo la exportación a PNG/Word (la combinación html2canvas + Tailwind v4 es la parte más delicada) y avise si algo no sale como se espera.

## 8novodecies. La exportación (PNG/Word con imágenes) no coincidía con la pantalla, y 4 unidades nuevas de "Grupo de Apoyo" (Skaven)

El usuario probó la ficha de 8octodecies y avisó de que exportar a PNG/Word con imágenes no salía "exactamente igual" que en pantalla — en concreto, el título se veía pegado al escudo/barra gris solo en el archivo exportado.

- **Causa: carrera de carga de tipografías en la exportación.** `offscreenRender.tsx` monta la tarjeta en un host oculto y solo esperaba a que las imágenes (`<img>`) cargasen antes de dejar que html2canvas capturase — nunca esperaba a que las tipografías de Google Fonts (Cinzel/PT Serif, añadidas en 8octodecies) terminasen de descargarse. La primera vez que se exporta tras abrir la app, html2canvas podía capturar el título todavía con la tipografía de reserva (Georgia) mientras Cinzel se descargaba en segundo plano — como cada fuente tiene una métrica distinta (alto de línea, ancho), el hueco calculado entre el título y la barra salía mal SOLO en esa captura; en la vista previa normal del navegador no se notaba porque para cuando el usuario mira la ficha la tipografía ya llevaba un rato cargada. Arreglado con `waitForFonts()` en `offscreenRender.tsx`: pide explícitamente la carga de los pesos usados (`document.fonts.load(...)` para Cinzel 600/700 y PT Serif 400/700/italic) y espera a `document.fonts.ready` antes de resolver, en paralelo con la espera de imágenes ya existente.
- **Causa adicional (preventiva): el truco de margen negativo del logo.** `.subbar .logo{margin:-14px 0}` (para que el escudo "asome" por encima y por debajo de la barra fina) es una combinación que varios motores de renderizado — html2canvas entre ellos, con reportes conocidos al respecto — no calculan siempre igual que un navegador real. Por si acaso era (total o parcialmente) la causa real en vez de/además de las tipografías, se sustituyó por una alternativa visualmente idéntica pero más robusta: el logo pasa a `position:absolute` centrado verticalmente (`top:50%;margin-top:-25px`) dentro de `.ficha-subbar` (que gana `position:relative` y el padding-left correspondiente para dejarle su hueco), en vez de ser un hijo flex con margen negativo — ver `.ficha-sheet .ficha-subbar .ficha-logo` en `index.css`.
- **4 unidades nuevas: "Grupo de Apoyo: Amerratadora/Lanzallamas/Mortero/Picadora" (Skaven).** El mecanismo de "Grupo de Apoyo" ya existía como 4 mejoras (`upgrades` id 21-24, ligadas a Guerreros Skaven/Alimañas) más una ficha genérica de unidad independiente ("Grupos de Apoyo", id 455, `category_id = NULL`, sin mejora fija) — ver 8quindecies. El usuario prefiere además tener cada variante como su PROPIA unidad seleccionable (coste ya fijado según el arma: Amerratadora 60, Lanzallamas 75, Mortero 50, Picadora 45), pidiendo explícitamente NO tocar las 4 mejoras existentes. Se crearon 4 unidades nuevas en Skaven (`category_id = NULL`, igual que la genérica; `min_size=max_size=default_size=1`; mismo perfil de atributos M12/HA3/HP3/F3/R3/H1/I4/A2/L5 que la genérica, en perfiles propios — no compartidos — para que editar uno desde Administración no afecte a los demás; mismas reglas especiales Hostigadores + Independiente tras el despliegue; `equipment_text` ya menciona el arma concreta de cada una), aplicado directamente contra D1 vía el conector MCP de Cloudflare (no vive en `seed-data.ts`, mismo criterio que las rondas de datos anteriores). Las 4 mejoras (21-24) y la unidad genérica (455) se dejaron intactas, tal como pidió el usuario — con lo que ahora coexisten ambas formas de usar el concepto (como mejora ligada a Guerreros Skaven/Alimañas, o como unidad suelta con arma fija); si en algún momento se quiere quitar la redundancia de la ficha genérica (455) frente a las 4 nuevas, habría que decidirlo explícitamente con el usuario.

## 8vicies. Por qué el blanco y negro salía tan oscuro, y un interruptor global de color/blanco y negro

El usuario adjuntó dos capturas de un mismo escudo (emblema) comparando esta app ("de ahora", muy oscuro, apenas se distingue el dibujo) contra CodexMaker ("anterior", gris claro, el dibujo se ve con detalle) y pidió arreglarlo para TODOS los emblemas, más un interruptor arriba del todo para ver todo el programa en blanco y negro o a color.

- **Causa encontrada: `resizeImageFile` "aplanaba" la transparencia a NEGRO, no a blanco.** Tanto el escudo de una ficha (`FichasPage.tsx`) como el emblema de una facción (`FactionFormModal.tsx`) pasan por la misma función de redimensionado (`shared/image.ts#resizeImageFile`), que dibuja la imagen subida sobre un `<canvas>` y la recomprime a JPEG para no guardar fotos enteras como BLOB. El canvas 2D es transparente por defecto, y JPEG no tiene canal alfa: al exportar, cualquier zona transparente del original (típico en un escudo recortado en PNG) se compone sobre NEGRO puro por defecto — el navegador no tiene ningún otro fondo que usar. En color, ese borde negro podía pasar desapercibido (a veces hasta parecía un marco "elegante"); pero un negro puro (RGB 0,0,0) se queda exactamente igual de oscuro lo mires en color o en blanco y negro, mientras que el resto del dibujo SÍ pierde matices al desaturarse — así que ese fondo negro terminaba dominando visualmente el icono entero en blanco y negro, mucho más que en color. Arreglado rellenando el canvas de BLANCO antes de dibujar la imagen encima (`ctx.fillStyle='#ffffff'; ctx.fillRect(...)`), para que la transparencia se aplane a blanco (un emblema con fondo recortado esperaría precisamente eso) en vez de a negro.
  - Esto arregla las PRÓXIMAS subidas; un escudo/emblema que ya se subió y se guardó con el fondo ya aplanado a negro no se puede recuperar automáticamente (la transparencia original ya no existe en el archivo guardado) — si el usuario nota algún emblema concreto con este problema, hay que volver a subirlo.
  - Los emblemas de fábrica (`public/assets/factions/*.jpg`) no pasan por esta función (son archivos ya fijos, nunca tuvieron transparencia que perder), así que no les afecta este bug ni necesitan ningún cambio.
- **Nuevo interruptor global "arriba del todo".** Antes solo existía el "Vista color/blanco y negro" de la sección Fichas (que controla la tarjeta y lo que se exporta — sigue igual). Ahora `TopNav.tsx` tiene un botón "Color"/"Blanco y negro" (icono `ContrastIcon`, mismo lenguaje visual que el de Fichas) visible en todas las pantallas, que aplica `filter:grayscale(100%)` al contenedor raíz de toda la app (`AppShell.tsx`) — como es un filtro CSS sobre TODO el árbol, afecta automáticamente a cualquier imagen/emblema en cualquier pantalla sin tener que tocar cada componente uno a uno. La preferencia se recuerda entre sesiones en `localStorage` (`useGrayscaleMode.ts`) por ser una preferencia de visualización del propio usuario, no un dato de la app. Es independiente del "Vista" de Fichas a propósito: uno es "cómo veo el programa mientras navego", el otro es "qué es lo que se exporta".

## 8unvicies. El escudo se montaba sobre el texto al exportar, e Ilustración/Escudo seguían saliendo con fondo (negro o blanco) en vez de sin fondo

Tres avisos en el mismo mensaje: quitar el subtítulo de la página Fichas, el escudo de la barra gris aparecía encima del texto SOLO al exportar a PNG, y las imágenes subidas (Ilustración/Escudo) seguían saliendo con un fondo feo en vez de sin fondo como en CodexMaker.

- **Quitado el subtítulo de "Fichas"** ("Ilustración, escudo y presentación de cada ficha — el resto se edita en Editor") — `PageHeader` ya admite no pasarle `description`.
- **Causa del escudo montado sobre el texto: OTRO caso de percentage/negative-margin poco fiable en html2canvas.** El arreglo de 8novodecies ya había cambiado el truco del logo (que "asoma" por encima y por debajo de la barra gris) de margen negativo sobre un hijo flex a `position:absolute;top:50%;margin-top:-25px` — pero un `top` en PORCENTAJE depende de que el motor de renderizado mida bien el alto real de `.ficha-subbar` (`height:auto`, no fijo), y html2canvas volvió a calcularlo mal: el logo aparecía mucho más abajo de lo que le tocaba, montado sobre el texto, solo en la exportación a PNG/Word con imágenes (en el navegador real se veía bien). Arreglado usando un `top` en PÍXELES FIJOS (`top:-15px`, sin porcentaje y sin margen negativo en un hijo flex) — un offset absoluto no depende de ninguna medición en tiempo de captura, así que cualquier motor de renderizado lo coloca siempre en el mismo sitio.
- **Causa del fondo feo en Ilustración/Escudo: `resizeImageFile` recomprimía SIEMPRE a JPEG.** El arreglo de 8vicies ya evitaba que la transparencia se aplanase a negro (rellenando de blanco antes de dibujar), pero seguía siendo un relleno SÓLIDO — JPEG no tiene canal alfa, así que por definición no puede dejar una imagen "sin fondo". Eso es aceptable para el emblema de una FACCIÓN (`factions.emblem_data`, que sí vive en el snapshot de catálogo descargado en cada carga de la app: JPEG más compacto importa ahí) pero NO para la Ilustración/Escudo de una FICHA (`unit_sheets`, deliberadamente excluida del snapshot — ver 8duodecies/schema.sql): esas imágenes se superponen FLOTANDO sobre la ficha, así que un recorte de personaje con fondo transparente tiene que seguir siéndolo, sin ningún rectángulo visible alrededor. `resizeImageFile` gana un parámetro `format` (`'image/jpeg'` por defecto, sin cambios para `FactionFormModal.tsx`; `'image/png'` para Ilustración y Escudo en `FichasPage.tsx`) que, cuando es PNG, se salta el relleno y conserva la transparencia real del archivo original.
  - Mismo aviso que en 8vicies: esto arregla las PRÓXIMAS subidas; una Ilustración/Escudo ya guardada con el fondo aplanado (blanco o negro) no se puede recuperar automáticamente — hay que volver a subirla.
